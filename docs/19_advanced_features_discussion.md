# 19. 고도화 논의 정리 (기획자 ↔ 개발자)

> **이 문서의 역할:** 고도화 방향에 대한 기획자·개발자 대화를 **결정된 것 / 아직 아닌 것**으로 갈라 정리한다.
> 아직 PRD가 아니다. 여기서 확정된 항목만 [PRD](./prd/README.md) 해당 SSOT 문서로 옮긴다.
> 원문 대화의 요지를 보존하되, 기존 제품 개념([01 홈](./prd/01-home-dashboard.md)·[02 사람](./prd/02-person.md)·[공통 기준 §12.2 칩](./prd/README.md#122-칩-개인화))과 어디서 겹치고 어디서 갈라지는지를 함께 표시한다.
> 대화 원문은 [부록](#부록-논의-전문)에 그대로 둔다.

## 0. 한 줄 요약

고도화 제안은 **세 갈래**다 — ① 사람을 사용자 정의 묶음(가칭 `그룹`)으로 나눠 홈에서 슬라이드로 넘겨 본다, ② 기록의 무게감을 낮춰 "스쳐 지나간 사람"까지 다 담는다, ③ 사람과 사람 사이의 **유대관계**를 드래그앤드롭으로 연결하는 마인드맵을 만든다.
이 중 **③은 방식까지 합의됐고**(→ `사이`로 확정, [§6](#6-진행-상황)), **①은 방향 합의·시각화 미정**, **②는 문제 정의가 도중에 바뀌어 결론이 없다**.

---

## 0.5 방향 결론

세 갈래가 따로 노는 것처럼 보이지만 한 문장으로 모인다.

> **내가 아는 모든 사람을, 내 언어로 분류해서, 서로 어떻게 얽혀 있는지 한 장의 지도로 본다.**

세 제안이 각각 이 문장의 한 조각이다.

| 제안 | 문장의 어느 조각인가 |
|---|---|
| "의미 없는 한 명도 다 기록되길 원했다" | **모든 사람** — 깊이보다 커버리지 |
| 어벤져스 / 스쳐 지나간 사람들 / 엑스들 | **내 언어로 분류** — 주어진 카테고리를 거부한다 |
| 유대관계 마인드맵 | **서로 얽힌 관계** — 나-사람 1:1을 넘어선다 |

### 그래서 실질적으로 바뀌는 것

**제품의 무게중심이 `기록`에서 `지도`로 옮겨간다.** 지금 제품은 사람 하나하나를 깊게 기록하고 회고하는 앱이고 타임라인이 핵심 자산이다([05 전체 타임라인](./prd/05-my-timeline.md)·[03 사람별 타임라인](./prd/03-timeline.md)). 고도화 논의는 전부 그 반대 방향을 가리킨다.

- **기록은 얕고 넓어진다.** 한 명당 깊은 타임라인을 쌓는 게 아니라 많은 사람을 가볍게 담는 쪽. 타임라인이 죽는 것은 아니고 주연에서 조연으로 내려온다 — 이어지는 관계에서만 자연히 쌓이는 부산물이 된다.
- **지도가 2차원으로 확장된다.** 그룹 = 지도를 여러 장으로 넘기는 축, 사이 = 한 장 안에서 노드끼리 잇는 축. 이 둘이 고도화의 실체이고 나머지는 그 귀결이다.

### 짚어둘 것

이 방향은 [PRD의 원래 문제 정의](./prd/README.md#2-문제-정의)("오랜만에 연락하거나 다시 만날 때, 상대의 취향과 최근 함께한 일을 떠올리기 어렵다")와 결이 다르다. 그건 **소수를 깊게 아는** 문제고, 이번 건 **다수를 넓게 훑는** 문제다.

둘 다 담을 수는 있다. 하지만 **홈에서 무엇을 먼저 보여줄지는 하나만 고를 수 있다.** 논의대로 가면 지도가 이긴다.

## 1. 그룹 — 사용자 정의 묶음 (가칭: 우주 / 방 / 마을)

### 제안 내용

`회사 / 가족 / 친구` 같은 사회적 분류가 아니라, **사용자가 이름과 의미를 직접 붙이는 플레이리스트형 묶음**.

| 사용자 지정 이름 | 그 이름이 의미하는 바 | 구성원 예시 |
|---|---|---|
| 어벤져스 | 내 인생의 구원자 | 미용사, 피부과 의사, 치과 의사, 이 차장님, 문 이사님 |
| 스쳐 지나간 사람들 | 소개팅했던 사람들 | 김와와, 박뫄뫄 |
| 엑스들 | 전남친들 | — |

- **핵심은 "이름"과 "의미"가 한 쌍이라는 것.** 묶음 자체가 사용자의 사적인 해석을 담는 그릇이다.
- 홈에서 보이는 관계 지도(가칭 `우주`)를 **좌우로 슬라이드**하면 사용자가 만든 그룹들로 넘어간다.

### 오간 질문과 답

- **개발자:** 그룹이 어떻게 시각화되나요? (예: 그 그룹 사람들만 뜨는 타임라인)
- **기획자:** **지금 메인 화면과 동일하게 나 중심으로 주변 인물을 표시**하고, 슬라이드로 넘길 때 그 **분류만 달라지는** 형태. 그룹별 **테마 설정**도 있으면 좋겠다.
- **개발자:** 그럼 기본 화면은 그룹이 아니라 개인(전체)인가요?
- **기획자:** 넵, 그게 더 좋겠다.

### 정리

| 항목 | 상태 |
|---|---|
| 그룹 = 사용자가 이름·의미를 붙이는 자유 묶음 | ✅ 합의 |
| 시각화 = 기존 관계 지도와 같은 나 중심 방사형, 슬라이드로 그룹 전환 | ✅ 합의 |
| 기본(첫) 화면 = 전체 보기, 그룹은 옆으로 넘겨서 진입 | ✅ 합의 |
| 그룹별 테마 | 🟡 하고 싶다는 의사만. 범위(배경/색/폰트?) 미정 |
| 그룹 전용 타임라인 | ❌ 논의됐으나 채택 안 됨 (지도 형태로 수렴) |

### 기존 개념과의 충돌 지점 (개발 관점 메모)

현재 PRD에는 이미 **관계태그**가 있다 — 인물에 붙는 개인용 칩, 인물당 최대 10개, 홈에서 다중 선택 OR 필터([01 §5](./prd/01-home-dashboard.md#5-정책), [§12.2](./prd/README.md#122-칩-개인화)). 데이터로 보면 `그룹`과 거의 같은 것이다(사람 ↔ 묶음 다대다).

차이는 셋뿐이다:

1. 그룹에는 **"의미" 설명 필드**가 붙는다 (관계태그엔 이름만 있다).
2. 관계태그는 **필터**(현재 지도를 좁힘)지만, 그룹은 **뷰의 단위**(슬라이드로 넘기는 별개의 지도)다.
3. 그룹은 **테마**를 가진다.

→ **첫 결정 포인트: 관계태그를 그룹으로 승격시킬 것인가, 별개 개념으로 둘 것인가.** 별개로 두면 사용자가 "회사 동료" 태그와 "회사" 그룹을 둘 다 만들게 되어 중복 관리 부담이 생긴다. 승격이 자연스러워 보이지만, 태그는 "여러 개 골라 넓혀 보기"가 전제고 그룹은 "한 번에 하나"가 전제라 상호작용 모델이 다르다는 점은 짚고 가야 한다.

## 2. 기록 · 일기 · 타임라인 — 무게감 문제

### 제안 내용

그룹 개념이 들어오면 **개인별 타임라인의 존재 의의가 약해진다**는 문제 제기.

기획자의 실제 논리는 "그룹이 생겨서"가 아니라 **기록 빈도** 쪽이었다:

> 누군가와의 기록을 매번 기록하기보단 **단건 단위로 한 번만** 기록하기 때문에 타임라인이 존재하는 의미가 없어진다.
> 한 번 보고 더 볼 일 없는 사람은 프로필 정도만 등록하면 되고, 나중에 다시 만나면 그때 타임라인을 이어가는 정도.
> **지금처럼 기록을 이어가는 느낌을 주면 한 명 한 명 기록하는 것에 무게감이 느껴질 것 같다. 나는 의미 없는 한 명도 다 기록되길 원했다.**

### 오간 질문과 답

- **개발자:** 처음 등록할 때 한 번에 메모해두고, 이어지는 관계일 때만 그때그때 기록하는 건가요? **여러 명을 쉽게 등록하고 싶은 니즈**가 있으신 것 같기도 하네요.
- **기획자:** 맞다. 다만 **"생각해보니 타임라인이 있든 없든 큰 차이는 없을 것 같기도"** 하다. 애매하다.

### 정리

| 항목 | 상태 |
|---|---|
| 타임라인 제거/축소 | ❌ **결론 없음.** 제안자 스스로 철회에 가깝게 후퇴 |
| 진짜 문제 = "한 명 기록하는 심리적 무게감" | ✅ 문제로는 합의 |
| 진짜 요구 = **여러 명을 가볍게 등록하기** | 🟡 개발자가 재해석해 제시, 기획자 동의. 해법은 미논의 |

### 개발 관점 메모

**타임라인을 건드리는 문제가 아니다.** 타임라인이 무거운 게 아니라 **"기록 없이 사람만 등록"이 자연스럽지 않은 것**이 원인에 가깝다.

현재 제품은 기록에 사람을 최소 1명 연결하도록 강제하지만([공통 기준 §12.1](./prd/README.md#121-하단-내비게이션)), 반대로 **사람에게 기록을 강제하지는 않는다** — 프로필만 등록하는 건 이미 된다. 그렇다면 남는 건 인식과 UX 문제다:

- 빈 타임라인의 빈 상태 문구("아직 함께한 기록이 없어요. 첫 순간을 새겨보세요.")가 **밀린 숙제처럼 읽힐 수 있다.** 기록 0건이 정상 상태인 사람이 다수라면 이 문구의 톤을 바꿔야 한다.
- **연속 등록 플로우**가 없다. "저장하고 계속 추가" 같은 경로, 혹은 이름만으로 최소 등록하는 경로가 있으면 "스쳐 지나간 사람들"을 무더기로 담는 행위가 가벼워진다.

→ **후속 확인 필요:** 무게감의 정체가 (a) 등록 폼이 길어서인지, (b) 기록이 없으면 미완성처럼 보여서인지, (c) 한 명씩만 등록해서인지. 셋의 해법이 전혀 다르다.

## 3. 유대관계 — 사람과 사람의 연결 (→ `사이`)

> 이 갈래는 구현까지 끝났다. 확정 스펙은 [PRD 01 §11](./prd/01-home-dashboard.md#11-사이-인물인물)이 SSOT다. 아래는 그 결론에 이르기까지의 논의다.

### 제안 내용

**그룹과는 다른 개념이다.** 기획자의 구분:

- **그룹** = 한 소속 안의 사람들을 보는 것 (회사 = 사내 인원, 가족 = 가족들, 친구 = 내 친구들)
- **유대관계** = *같이 아는 사이 / 함께 아는 친구*
  - 직장동료 A와 친구 B가 아는 사이
  - 친언니와 직장동료 B를 소개시켜줘서 아는 사이
  - 친구 A에게 회사원 D를 소개시켜줘서 아는 사이

→ 그래서 **마인드맵처럼 연결**하면 좋겠다.

요구사항:
- 유대관계가 없는 사람은 **연결선 없이 외곽에 프로필만** 떠 있다.
- **드래그앤드롭으로 관련 있는 사람 프로필 위에 얹으면 유대관계 형성.**

### 오간 질문과 답

- **개발자:** 유대관계 관리가 조금 복잡해질 수 있으니 우선 **드래그로 연결, 연결선을 터치하면 메뉴가 떠서 제거**하는 정도로 간단히 풀자.
- **기획자:** 👍 (합의)

### 정리

| 항목 | 상태 |
|---|---|
| 유대관계 ≠ 그룹, 별개 개념 | ✅ 합의 |
| 사람 ↔ 사람 연결을 그래프에 표현 | ✅ 합의 |
| 연결 없는 사람은 외곽에 프로필만 | ✅ 합의 |
| 생성 = 드래그앤드롭으로 프로필 위에 얹기 | ✅ 합의 |
| 삭제 = 연결선 터치 → 메뉴 → 제거 | ✅ 합의 |
| **명칭** | ✅ **`사이`** 로 확정 |
| 연결의 방향·라벨 (누가 누구를 소개했는지) | ✅ **담지 않기로** 결정 (아래) |

**소개 정보를 담지 않은 이유:** 기획자 예시 세 개 중 둘이 "소개시켜줘서"라 방향 있는 정보로 볼 여지가 있었다. 다만 소개는 사이가 생긴 **계기**일 뿐이고, 그것까지 담으면 잇는 동작이 무거워진다("가볍게 잇기"가 이 기능의 전제다). 선에 계기를 남기고 싶다는 요구가 실제로 나오면 그때 확장한다.

### 개발 관점 메모

이 요구는 **현재 관계 지도의 성격을 바꾼다.** 지금은 `나 → 사람` 방사형 한 겹인데, 사이가 들어오면 `사람 ↔ 사람` 엣지가 생겨 진짜 그래프가 된다. 파급:

- **레이아웃:** "연결 없는 사람은 외곽" 규칙이 곧 레이아웃 알고리즘의 제약이 된다. 연결된 무리는 안쪽에 뭉치고 고립 노드는 바깥 링에 배치되는 형태.
- **과밀:** PRD에 이미 "인원이 많으면 리스트로 보기를 권한다"는 케이스가 있는데([01 §6](./prd/01-home-dashboard.md#6-상태엣지케이스)), 엣지까지 늘면 그 임계가 훨씬 빨리 온다. 여기서 **그룹 슬라이드가 과밀의 해법 역할**을 겸할 수 있다 — 한 화면에 한 그룹만 그리면 노드 수가 자연히 줄어든다. 두 기능이 이 지점에서 맞물린다.
- **모바일 드래그앤드롭:** 지도 자체의 팬/줌 제스처와 노드 드래그가 충돌한다. 롱프레스로 드래그 모드에 진입하는 식의 분리가 필요하다. → 실제로 구현의 대부분이 이 정리였다([mustpass](../frontend/docs/mustpass/relation-bond.md)).

## 4. 확정되지 않은 것 — 기획자에게 되물을 목록

`사이`(§3)에서 나온 항목은 확정돼 빠졌다. 남은 것은 모두 **그룹**과 **기록 무게감** 쪽이다.

1. **묶음의 이름을 뭐라고 부를 것인가.** 우주 / 방 / 마을 중 미정. 제품 전반의 문구가 여기 걸린다.
2. **그룹과 기존 관계태그를 합칠 것인가.** (→ [§1 충돌 지점](#기존-개념과의-충돌-지점-개발-관점-메모))
3. **한 사람이 여러 그룹에 속할 수 있는가.** ("스쳐 지나간 사람들"이자 "어벤져스"일 수 있는지)
4. **그룹에 속하지 않은 사람은 어디에 보이는가.** 전체 보기에만? 미분류 그룹?
5. **"테마"의 범위.** 배경색 정도인지, 배경 이미지·분위기까지인지.
6. **무게감의 정체.** 등록 폼 길이인지, 빈 타임라인이 주는 압박인지, 연속 등록의 부재인지. (→ [§2 개발 관점 메모](#개발-관점-메모))

> **1·2·3은 데이터 모델을 좌우**하므로 그룹 착수 전에 답을 받아야 한다.

## 5. 다음 단계

- **`사이`는 완료.** → [§6](#6-진행-상황)
- **그룹**은 위 1·2·3의 답을 받고 착수한다. 사이가 깔아 둔 사람↔사람 엣지 위에 슬라이드를 얹는 순서가 자연스럽다.
- **기록 무게감은 아직 스펙을 쓰지 않는다.** 문제 정의가 흔들린 채라, 무게감의 정체(§4-6)를 확인한 뒤 다시 잡는다.
